Tutoriel dbt — Core, Cloud et intégration Airflow

Référence pratique : ce que fait chaque outil, comment ils s'articulent, et les commandes à connaître.

Comment s'articulent dbt Core, dbt Cloud et Airflow

Ces trois outils ne sont pas en concurrence directe, ils répondent à des questions différentes :

OutilRépond à la questionCe qu'il n'est pas
dbt CoreComment transformer mes données déjà chargées, avec des tests et de la doc, en écrivant du SQL ?Un outil d'extraction de données, ni un scheduler
dbt CloudComment développer, planifier et héberger tout ça sans gérer d'infrastructure moi-même ?Un remplaçant de dbt Core — c'est dbt Core, packagé avec un IDE web, un scheduler et un hébergement
AirflowComment orchestrer plusieurs pipelines (extraction, dbt, entraînement ML, envoi de rapport…) dans le bon ordre, avec retries et alerting ?Un outil de transformation SQL — Airflow ne sait pas ce qu'est un modèle dbt, il sait juste lancer des commandes/tâches
Repère simple : dbt (Core ou Cloud) répond à « comment transformer ». Airflow répond à « quand et dans quel ordre, avec quoi d'autre ». On utilise souvent Airflow pour déclencher dbt, jamais l'inverse.

1. dbt Core

dbt Core est l'outil en ligne de commande, gratuit et open source. Tout ce qui suit fonctionne en local, sans compte ni service externe (à part ton entrepôt de données).

1.1 Installation & connexion

python -m venv .venv
source .venv/bin/activate
pip install dbt-core dbt-duckdb   # l'adaptateur dépend de ton entrepôt : dbt-postgres, dbt-snowflake, dbt-bigquery...
dbt --version

La connexion à l'entrepôt se configure dans ~/.dbt/profiles.yml (hors du projet, pour ne jamais versionner de secrets) :

# ~/.dbt/profiles.yml
mon_projet:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: warehouse.duckdb
      threads: 4

1.2 Structure d'un projet

mon_projet/
├── dbt_project.yml       # config du projet (nom, matérialisation par défaut, dossiers)
├── models/
│   ├── staging/          # nettoyage 1:1 des sources
│   ├── intermediate/     # jointures, agrégations partielles
│   └── marts/            # tables finales (faits/dimensions)
├── tests/                # tests SQL "singuliers" (custom)
├── macros/               # fonctions Jinja réutilisables
├── seeds/                # petits CSV chargés tels quels
├── snapshots/            # historisation de type SCD2
└── analyses/             # requêtes ad-hoc, non matérialisées

1.3 Commandes essentielles

CommandeÀ quoi elle sert
dbt debugVérifie la config et la connexion à l'entrepôt
dbt depsInstalle les packages déclarés dans packages.yml
dbt seedCharge les CSV du dossier seeds/
dbt runConstruit les modèles (dans l'ordre du DAG)
dbt testExécute tous les tests déclarés
dbt buildFait seed + run + test + snapshot, dans l'ordre du DAG, modèle par modèle (recommandé au quotidien)
dbt compileTraduit le Jinja/SQL en SQL brut, sans l'exécuter
dbt docs generateGénère la documentation (catalogue + manifest)
dbt docs serveSert la doc dans un navigateur en local
dbt lsListe les ressources du projet (modèles, tests…) sans les exécuter
dbt cleanSupprime target/ et les packages installés

1.4 Models & matérialisations

Un modèle est un fichier .sql contenant un SELECT. La matérialisation définit comment dbt le construit dans l'entrepôt :

MatérialisationComportementQuand l'utiliser
viewRecalculée à chaque lecturePar défaut, modèles légers ou peu consultés (souvent staging)
tableStockée physiquement, reconstruite entièrement à chaque runModèles lourds à calculer, consultés souvent (souvent marts)
incrementalAjoute seulement les nouvelles lignes au lieu de tout recalculerGrosses tables qui grossissent dans le temps (logs, transactions)
ephemeralN'existe pas dans l'entrepôt, injectée comme sous-requête (CTE) dans les modèles qui la référencentÉtape de nettoyage intermédiaire très légère, jamais interrogée seule
-- déclarer la matérialisation en haut du fichier
{{ config(materialized='table') }}

select ...
from {{ ref('stg_kiva_loans') }}

1.5 Tests

Tests génériques (déclaratifs, en YAML) :

models:
  - name: fact_loans
    columns:
      - name: loan_id
        tests: [not_null, unique]
      - name: status
        tests:
          - accepted_values:
              values: ['funded', 'in_repayment', 'paid']

Tests singuliers (une requête SQL qui doit renvoyer 0 lignes pour passer), dans tests/ :

-- tests/assert_no_negative_amounts.sql
select * from {{ ref('fact_loans') }}
where amount < 0

Packages utiles : dbt-utils (tests génériques additionnels), dbt_expectations (tests façon Great Expectations).

1.6 Documentation

Les descriptions se déclarent dans les fichiers .yml à côté des modèles (description: sur un modèle ou une colonne). dbt docs generate construit un site statique consultable avec dbt docs serve, incluant le DAG interactif du projet.

1.7 Macros & Jinja

dbt utilise Jinja pour du SQL dynamique : boucles, conditions, réutilisation de logique.

-- macros/cents_to_amount.sql
{% macro cents_to_amount(column_name) %}
    ({{ column_name }} / 100.0)
{% endmacro %}

-- utilisation dans un modèle
select {{ cents_to_amount('amount_cents') }} as amount
from {{ source('raw', 'loans') }}

1.8 Packages

# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.0.0", "<2.0.0"]
dbt deps   # à relancer après chaque modification de packages.yml

1.9 Snapshots

Un snapshot capture l'état d'une table à chaque exécution pour reconstituer son historique (type SCD2 — utile quand la source ne garde pas l'historique elle-même, ex. le statut d'un prêt qui change dans le temps).

1.10 Seeds

Les seeds sont des petits fichiers CSV versionnés dans le projet et chargés tels quels avec dbt seed (utile pour des référentiels fixes : liste de pays, mapping de codes).

1.11 Sources & freshness

# models/staging/_sources.yml
sources:
  - name: raw
    tables:
      - name: kiva_loans
        loaded_at_field: extracted_at
        freshness:
          warn_after: {count: 24, period: hour}
          error_after: {count: 48, period: hour}

dbt source freshness vérifie que les données brutes ne sont pas périmées avant de lancer les transformations.

1.12 Environnements & targets

Un même profiles.yml peut définir plusieurs cibles (dev, prod), chacune pointant vers un schéma ou une base différente. On choisit la cible avec dbt run --target prod.

1.13 Modèles incrémentaux

{{ config(materialized='incremental', unique_key='loan_id') }}

select * from {{ source('raw', 'kiva_loans') }}

{% if is_incremental() %}
  where extracted_at > (select max(extracted_at) from {{ this }})
{% endif %}

1.14 Sélecteurs de graphe

CommandeEffet
dbt run --select stg_kiva_loansUn seul modèle
dbt run --select stg_kiva_loans+Ce modèle et tout ce qui en dépend en aval
dbt run --select +fact_loansCe modèle et tout ce dont il dépend en amont
dbt run --select tag:martsTous les modèles tagués marts
dbt run --select state:modified+Les modèles modifiés depuis le dernier run (Slim CI) et leur aval

2. dbt Cloud

2.1 Qu'est-ce que c'est

dbt Cloud est un service managé développé par dbt Labs : il fait tourner dbt Core en arrière-plan, mais t'évite de gérer l'infrastructure. En plus des commandes dbt classiques, il ajoute :

  • Un IDE web pour écrire et tester tes modèles sans rien installer en local.
  • Un scheduler intégré (jobs planifiés) — pas besoin d'Airflow ou de cron pour les cas simples.
  • Un hébergement automatique de la documentation générée par dbt docs generate.
  • Une intégration Git native (branches, pull requests, jobs CI déclenchés sur PR).
  • Une offre gratuite (Developer plan, un seul développeur) suffisante pour apprendre.
Important : dbt Cloud n'est pas un langage différent — le SQL et le YAML que tu écris sont strictement les mêmes qu'en dbt Core. Ce que tu apprends en Core (week-ends 3 et 4 du guide projet) est directement réutilisable en Cloud.

2.2 Créer un projet

  1. Créer un compte sur getdbt.com (offre Developer gratuite).
  2. Connecter un entrepôt de données (BigQuery, Snowflake, Postgres… — DuckDB local n'est pas supporté par dbt Cloud, il faut un entrepôt accessible sur le réseau).
  3. Connecter ton dépôt GitHub (dbt Cloud clone et gère les branches pour toi).
  4. Créer un environnement de développement, puis un environnement de déploiement (production).

2.3 IDE & Git

L'IDE web permet d'éditer les modèles, de lancer dbt run/dbt test sur une branche de développement, de committer et d'ouvrir une pull request directement depuis l'interface. Le flux de travail Git (branche, commit, PR, review, merge) reste le même qu'en local.

2.4 Jobs & environnements

Un job dbt Cloud définit une suite de commandes (ex. dbt build) à exécuter, sur un environnement donné, selon un déclencheur :

Type de déclencheurUsage typique
Planifié (cron)Rafraîchir les données de production chaque nuit
Sur webhook / APIDéclenché par un outil externe (ex. Airflow, une extraction terminée)
CI sur pull requestConstruit uniquement les modèles modifiés (Slim CI) avant de merger

2.5 Cloud vs Core : que choisir

Critèredbt Coredbt Cloud
CoûtGratuitGratuit pour 1 développeur, payant en équipe
SchedulerÀ gérer soi-même (cron, Airflow…)Intégré
Hébergement de la docÀ héberger soi-mêmeAutomatique
Entrepôt local (DuckDB)SupportéNon supporté
Apprentissage en soloIdéal — tu vois tout ce qui se passePratique une fois les bases acquises

Pour ce projet : reste sur dbt Core en local pendant tout le guide d'apprentissage (tu contrôles chaque étape). Tu pourras créer un compte dbt Cloud gratuit ensuite, juste pour voir l'IDE et les jobs tourner sur le même projet, sans réécrire de code.

3. dbt + Airflow

3.1 Pourquoi orchestrer dbt avec Airflow

dbt Core seul n'a pas de scheduler : il faut quelque chose d'externe (cron, Airflow, dbt Cloud) pour le déclencher régulièrement. Airflow devient pertinent quand dbt n'est qu'une étape parmi d'autres (après une extraction, avant l'entraînement d'un modèle ML, avant l'envoi d'un rapport) et que tu as besoin de dépendances entre ces étapes, de retries, d'alerting et d'un historique d'exécution.

3.2 Option A — BashOperator

Le plus simple

Une ou deux tâches Airflow qui lancent directement les commandes dbt en shell.

from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime

DBT_DIR = "/opt/airflow/dbt/mon_projet"

with DAG("dbt_pipeline", start_date=datetime(2026, 1, 1), schedule="@daily", catchup=False) as dag:
    dbt_run = BashOperator(
        task_id="dbt_run",
        bash_command=f"cd {DBT_DIR} && dbt run --target prod",
    )
    dbt_test = BashOperator(
        task_id="dbt_test",
        bash_command=f"cd {DBT_DIR} && dbt test --target prod",
    )
    dbt_run >> dbt_test

Limite : Airflow voit deux grosses tâches (« dbt_run », « dbt_test »), pas le détail modèle par modèle. Si un modèle échoue au milieu de 20, tout dbt_run est marqué en échec sans granularité.

3.3 Option B — Cosmos (astronomer-cosmos)

Le plus utilisé en production

Cosmos est un package qui lit le graphe dbt et génère automatiquement une tâche Airflow par modèle dbt, avec les bonnes dépendances entre elles. Tu vois chaque modèle individuellement dans l'interface Airflow.

pip install astronomer-cosmos
from cosmos import DbtDag, ProjectConfig, ProfileConfig
from datetime import datetime

project_config = ProjectConfig("/opt/airflow/dbt/mon_projet")
profile_config = ProfileConfig(
    profile_name="mon_projet",
    target_name="prod",
    profiles_yml_filepath="/opt/airflow/dbt/mon_projet/profiles.yml",
)

dbt_dag = DbtDag(
    project_config=project_config,
    profile_config=profile_config,
    schedule="@daily",
    start_date=datetime(2026, 1, 1),
    dag_id="dbt_cosmos_pipeline",
)

Avantage : granularité fine (retry un seul modèle en échec, pas tout le projet), visualisation du vrai DAG dbt dans Airflow.

3.4 Option C — Déclencher dbt Cloud depuis Airflow

Si tu utilises dbt Cloud

Le package apache-airflow-providers-dbt-cloud fournit un opérateur qui déclenche un job dbt Cloud existant et attend sa fin, sans exécuter dbt directement sur les workers Airflow.

pip install apache-airflow-providers-dbt-cloud
from airflow.providers.dbt.cloud.operators.dbt import DbtCloudRunJobOperator
from airflow import DAG
from datetime import datetime

with DAG("dbt_cloud_trigger", start_date=datetime(2026, 1, 1), schedule="@daily") as dag:
    trigger_job = DbtCloudRunJobOperator(
        task_id="trigger_dbt_cloud_job",
        dbt_cloud_conn_id="dbt_cloud_default",
        job_id=123456,
        wait_for_termination=True,
    )

Avantage : l'exécution reste gérée par dbt Cloud (logs, doc, historique), Airflow ne fait que déclencher et attendre.

3.5 Comparatif

OptionGranularitéComplexité de mise en placeQuand l'utiliser
BashOperatorFaible (tout ou rien)Très simpleApprentissage, petit projet solo
CosmosFine (par modèle)MoyenneProjet dbt Core en production, équipe
dbt Cloud + providerGérée par dbt CloudFaible si dbt Cloud déjà en placeTu utilises déjà dbt Cloud pour le scheduling de base, Airflow orchestre juste l'ensemble plus large

Pour le guide projet (week-end 5) : commence par l'option BashOperator — c'est suffisant pour comprendre le principe d'orchestration sans complexité supplémentaire. Cosmos est une extension naturelle une fois à l'aise.

3.6 Bonnes pratiques

  • Toujours enchaîner dbt run puis dbt test (ou directement dbt build) — ne jamais laisser des modèles non testés partir en aval.
  • Configurer des retries sur les tâches Airflow pour absorber les erreurs transitoires (timeout réseau, entrepôt temporairement indisponible).
  • Séparer les cibles dev et prod dans profiles.yml, ne jamais faire tourner un DAG de développement sur le schéma de production.
  • Utiliser les sélecteurs dbt (state:modified+) pour ne reconstruire que ce qui a changé sur les DAGs déclenchés par un CI.
  • Faire remonter les échecs de tests dbt comme des échecs de tâche Airflow (le exit code non-zéro de dbt test suffit avec BashOperator).

4. Aide-mémoire des commandes

dbt debug                        # vérifie la connexion
dbt deps                         # installe les packages
dbt seed                         # charge les CSV de seeds/
dbt run                          # construit les modèles
dbt run --select stg_kiva_loans  # un seul modèle
dbt run --select stg_kiva_loans+ # ce modèle + son aval
dbt test                         # lance tous les tests
dbt build                        # seed + run + test + snapshot, dans l'ordre
dbt docs generate && dbt docs serve   # doc + DAG interactif
dbt source freshness             # vérifie la fraîcheur des sources
dbt compile                      # affiche le SQL compilé sans l'exécuter
dbt clean                        # nettoie target/ et les packages
