Génération de tests dbt et documentation par LLM

Guide d'apprentissage pas à pas — niveau débutant absolu

Comment utiliser ce document

Ce n'est pas un tutoriel à copier-coller. Chaque séance suit toujours le même schéma :

  • Objectif — ce que tu dois avoir accompli à la fin des 2h.
  • Concept — une explication courte, en langage simple.
  • Exemple guidé — un exemple générique (pas ton projet), pour montrer la mécanique.
  • À toi de jouer — la tâche précise que tu fais toi-même, sur ton projet.
  • Indice si tu bloques — une piste, pas la solution toute faite.
  • Tu as réussi si — un critère concret pour t'auto-évaluer.
Règle d'or : tu as le droit d'utiliser l'IA pour comprendre une erreur ou un concept, jamais pour écrire le code à ta place. Si une IA te répond avec un bloc de code entier prêt à coller : ignore le code, ne garde que l'explication.

Évaluation honnête du projet

L'idée de départ (300+ modèles dbt, 3 sources de données, Great Expectations, Airflow, MLflow, protocole d'évaluation publiable) est un sujet de recherche de plusieurs mois, pas un projet de week-end. Avec ton budget réel — 2h vendredi, 2h samedi, 2h dimanche, soit 6h/semaine — il faut réduire le périmètre pour un objectif honnête : apprendre vraiment chaque brique, pas juste avoir un dossier qui tourne.

Sacrifier la compréhension pour la vitesse, c'est exactement le piège de laisser l'IA faire à ta place.

Glossaire express

  • ETL vs ELT — ETL transforme les données avant de les charger. ELT charge les données brutes d'abord, puis transforme dans l'entrepôt (c'est ce que fait dbt).
  • Data warehouse — une base optimisée pour l'analyse (lecture de gros volumes), pas pour les transactions unitaires. Ici : DuckDB.
  • Staging — première couche de modèles dbt : nettoie et renomme les données brutes, sans changer leur granularité.
  • Intermediate — couche intermédiaire : jointures et agrégations partielles.
  • Marts — couche finale, prête à être consommée. Souvent organisée en faits/dimensions (schéma en étoile).
  • Table de faits — contient les événements mesurables (ex : un prêt accordé, avec son montant).
  • Table de dimension — contient le contexte descriptif (ex : un pays, un secteur, une date).
  • Matérialisation dbt — façon dont dbt construit un modèle (view = recalculée à chaque lecture, table = stockée physiquement).
  • DAG — graphe orienté acyclique : les dépendances entre modèles (ou tâches Airflow) sous forme de flèches sans boucle.
  • Orchestrateur — déclenche et planifie l'exécution de tâches dans le bon ordre, avec retry en cas d'échec (ici : Airflow).
  • Profiling de données — calculer des statistiques descriptives sur une colonne (taux de nulls, valeurs distinctes, min/max) avant d'écrire des tests.
  • Test dbt — une assertion SQL qui échoue si une condition n'est pas respectée (not_null, unique, accepted_values, relationships).
  • Faux positif (ici) — un test généré par le LLM qui semble raisonnable mais casse sur les vraies données ou n'a pas de sens métier.
  • Précision / rappel (version simple) — précision = part des tests proposés par le LLM qui sont réellement pertinents ; rappel = part des tests qu'un humain aurait écrits que le LLM a retrouvés.

Avant de commencer : comptes et outils

À faire une seule fois (prévois une petite session dédiée, ça ne compte pas dans les sprints) :

  1. Un compte GitHub (déjà fait) + un nouveau dépôt vide, ex. dbt-llm-quality.
  2. Python 3.10+ et savoir créer un environnement virtuel (python -m venv .venv).
  3. Un compte sur console.mistral.ai pour une clé API gratuite. Alternative : console.groq.com, gratuit et très rapide, pour des modèles ouverts (Llama, Mixtral).
  4. Docker (nécessaire à partir du week-end 5, pour Airflow). Pas de GPU, pas de modèle local : tout passe par l'API.
  5. Un éditeur de code (VS Code par exemple) avec l'extension Python.

Feuille de route en sprints (week-ends)

Chaque week-end = 3 séances de 2h (vendredi, samedi, dimanche). Ne saute pas une séance même en avance : utilise le temps en plus pour lire la doc officielle plutôt que d'avancer sans comprendre.

Week-end 1 — Fondations et environnement

Vendredi — mise en place

ObjectifAvoir un dépôt Git local relié à GitHub, un environnement Python fonctionnel, dbt installé.
Concept à connaîtredbt (data build tool) transforme des données déjà chargées dans un entrepôt en écrivant simplement des requêtes SELECT. Il gère l'ordre d'exécution, les tests et la documentation.
Exemple guidé (générique) 
python -m venv .venv && source .venv/bin/activate
pip install dbt-core dbt-duckdb
dbt --version
À toi de jouerCrée le dépôt GitHub dbt-llm-quality, clone-le en local, crée et active un environnement virtuel, installe dbt-core et dbt-duckdb, vérifie avec dbt --version.
Indice si tu bloquesSi dbt --version ne trouve pas la commande, vérifie que ton environnement virtuel est activé (le prompt doit afficher (.venv)).
Tu as réussi sidbt --version affiche une version, et git status ne montre pas d'erreur.

Samedi — comprendre le schéma cible

ObjectifAvoir dessiné (papier ou fichier texte) le schéma en étoile de ton projet.
Concept à connaîtreUn schéma en étoile a une table de faits au centre (les événements) entourée de tables de dimension (le contexte). Ex. e-commerce : faits = ventes, dimensions = client, produit, date, magasin.
Exemple guidé (générique)fact_orders (montant, quantité, id_client, id_produit, id_date) entourée de dim_customer, dim_product, dim_date.
À toi de jouerDessine (à la main ou dans un fichier schema.md) le schéma cible pour les prêts Kiva : quelle table de faits ? Quelles dimensions (pays, secteur, date, statut) ?
Indice si tu bloquesUn prêt Kiva a un montant, une date, un pays, un secteur, un statut. Le montant est une mesure numérique agrégeable ⇒ bon candidat pour la table de faits.
Tu as réussi siTu peux expliquer à voix haute, sans notes, pourquoi telle donnée est dans les faits et telle autre dans une dimension.

Dimanche — accès à l'API LLM gratuite

ObjectifAvoir une clé API Mistral (ou Groq) fonctionnelle, testée avec un appel simple.
Concept à connaîtreUne API LLM « gratuite » a presque toujours une limite de requêtes/minute ou /jour. On l'appelle en HTTP POST avec un prompt ; elle répond en texte généré.
Exemple guidé (générique) 
import os, requests

resp = requests.post(
    "https://api.mistral.ai/v1/chat/completions",
    headers={"Authorization": f"Bearer {os.environ['MISTRAL_API_KEY']}"},
    json={
        "model": "mistral-small-latest",
        "messages": [{"role": "user", "content": "Dis bonjour en une phrase."}],
    },
)
print(resp.json())
À toi de jouerCrée ta clé API, stocke-la en variable d'environnement (jamais dans le code ni sur GitHub), écris test_llm.py qui envoie un prompt simple et affiche la réponse.
Indice si tu bloquesAjoute .env et tout fichier contenant ta clé à .gitignore avant ton premier commit, pas après.
Tu as réussi siTon script affiche une réponse cohérente, et git log ne contient ta clé nulle part.

Week-end 2 — Extraction des données (Extract)

Vendredi — explorer l'API Kiva

ObjectifComprendre la structure des données Kiva et récupérer un premier échantillon.
Concept à connaîtreUne API REST publique expose des endpoints qui renvoient du JSON, généralement paginés (page, limit).
Exemple guidé (générique) 
import requests
r = requests.get("https://api.publicapis.org/entries", params={"limit": 5})
print(r.status_code)
print(r.json())
À toi de jouerTrouve dans la doc Kiva l'endpoint qui liste les prêts, fais un appel avec un limit petit (10-20), inspecte les champs (montant, pays, secteur, statut, date).
Indice si tu bloquesSi l'API historique n'est plus dispo telle quelle, cherche leur data snapshot public (souvent en CSV/JSON téléchargeable) : ça reste une extraction, juste par fichier plutôt que par requête live.
Tu as réussi siTu as un JSON/DataFrame avec au moins 100 prêts et tu peux lister les colonnes disponibles.

Samedi — script d'extraction complet

ObjectifUn script Python réutilisable qui récupère N prêts et les sauvegarde en local.
Concept à connaîtreSéparer extraction et transformation : le script d'extraction ne nettoie ni ne transforme, il sauvegarde « brut » (raw). Le nettoyage, c'est dbt plus tard.
À toi de jouerÉcris extract_kiva.py qui boucle sur plusieurs pages, agrège les résultats, écrit data/raw/kiva_loans.csv (ou .parquet).
Indice si tu bloquespandas.DataFrame(liste_de_dicts) puis .to_csv(...) convertit simplement une liste de résultats JSON en fichier tabulaire.
Tu as réussi siLe fichier existe, s'ouvre correctement, et relancer le script ne casse rien (idempotent).

Dimanche — charger dans DuckDB + Findex

ObjectifCharger les données brutes dans une base DuckDB locale, schema raw, et ajouter le CSV Findex.
Concept à connaîtreDuckDB est une base analytique qui vit dans un simple fichier .duckdb, sans serveur. On charge un CSV directement en SQL avec read_csv_auto.
Exemple guidé (générique) 
import duckdb
con = duckdb.connect("warehouse.duckdb")
con.execute("CREATE SCHEMA IF NOT EXISTS raw;")
con.execute("""
  CREATE OR REPLACE TABLE raw.example AS
  SELECT * FROM read_csv_auto('data/raw/example.csv')
""")
À toi de jouerCharge kiva_loans.csv dans raw.kiva_loans, télécharge le CSV Global Findex (Banque mondiale) et charge-le dans raw.findex.
Indice si tu bloquescon.sql("SELECT * FROM raw.kiva_loans LIMIT 5").show() pour vérifier visuellement.
Tu as réussi siSELECT COUNT(*) FROM raw.kiva_loans renvoie un nombre cohérent, pareil pour raw.findex.

Week-end 3 — dbt : les fondamentaux

Vendredi — initialiser le projet dbt

ObjectifUn projet dbt initialisé, connecté à ton fichier DuckDB, avec un premier modèle staging qui compile.
Concept à connaîtreUn modèle dbt est un fichier .sql contenant un SELECT. dbt le transforme en CREATE VIEW ou CREATE TABLE. sources.yml déclare où sont tes tables brutes.
Exemple guidé (générique) 
-- models/staging/stg_example.sql
select
    id,
    lower(trim(country)) as country,
    amount::double as amount
from {{ source('raw', 'example') }}
À toi de jouerdbt init, configure profiles.yml vers ton fichier DuckDB, déclare raw.kiva_loans et raw.findex dans sources.yml, écris stg_kiva_loans.sql (nettoie/renomme 5-6 colonnes).
Indice si tu bloquesdbt debug te dit précisément ce qui cloche (chemin du fichier, profil introuvable, etc.).
Tu as réussi sidbt run --select stg_kiva_loans se termine avec « Completed successfully ».

Samedi — comprendre ref(), source() et le DAG

ObjectifVisualiser le graphe de dépendances de ton projet dbt.
Concept à connaîtresource() pointe vers une table brute, ref() vers un autre modèle dbt. C'est ce qui permet à dbt de construire automatiquement l'ordre d'exécution (le DAG).
À toi de jouerAjoute stg_findex.sql, puis dbt docs generate && dbt docs serve, explore le graphe dans le navigateur.
Indice si tu bloquesLe DAG doit montrer une flèche de chaque source vers son modèle staging — si rien n'apparaît, vérifie que tu utilises bien source() et pas le nom de table en dur.
Tu as réussi siTu vois le DAG dans ton navigateur avec au moins 2 sources et 2 modèles staging reliés.

Dimanche — premiers tests natifs

ObjectifTrois tests dbt natifs qui passent sur tes modèles staging.
Concept à connaîtreLes tests génériques dbt (not_null, unique, accepted_values, relationships) se déclarent en YAML, à côté des modèles.
Exemple guidé (générique) 
# models/staging/_stg_example.yml
models:
  - name: stg_example
    columns:
      - name: id
        tests: [not_null, unique]
      - name: country
        tests: [not_null]
À toi de jouerÉcris _stg_kiva_loans.yml avec au moins 3 tests pertinents (id unique et non nul, amount non nul, status avec accepted_values sur les statuts réels observés).
Indice si tu bloquesRegarde d'abord les valeurs réelles avec SELECT DISTINCT status FROM stg_kiva_loans avant d'écrire accepted_values, sinon le test échouera à tort.
Tu as réussi sidbt test affiche PASS sur les 3 tests (ou tu comprends et corriges un échec légitime).

Week-end 4 — Modélisation de l'entrepôt (intermediate et marts)

Vendredi — tables de dimension

Objectif2 à 3 tables de dimension propres (dim_country, dim_sector, dim_date).
Concept à connaîtreUne dimension contient une ligne unique par entité, souvent avec une clé de substitution (surrogate key) générée par hachage.
Exemple guidé (générique) 
select distinct
    {{ dbt_utils.generate_surrogate_key(['country']) }} as country_key,
    country
from {{ ref('stg_kiva_loans') }}
À toi de jouerInstalle dbt-utils (packages.yml + dbt deps), crée dim_country.sql et dim_sector.sql dans models/marts/.
Indice si tu bloquesdbt deps doit être relancé à chaque modification de packages.yml.
Tu as réussi siChaque dimension a un nombre de lignes = nombre de valeurs distinctes réelles (vérifie avec un GROUP BY manuel).

Samedi — table de faits

Objectiffact_loans qui référence les dimensions par clé étrangère.
À toi de jouerConstruis fact_loans.sql en joignant stg_kiva_loans à dim_country et dim_sector pour récupérer leurs clés.
Indice si tu bloquesSi une jointure produit plus de lignes que prévu, c'est probablement une dimension avec des doublons : vérifie dim_country avec un test unique.
Tu as réussi siSELECT COUNT(*) FROM fact_loans = même nombre de lignes que stg_kiva_loans (pas de duplication).

Dimanche — tests relationnels et documentation

ObjectifDes tests relationships entre faits et dimensions, et une description pour chaque modèle/colonne clé.
Exemple guidé (générique) 
columns:
  - name: country_key
    tests:
      - relationships:
          to: ref('dim_country')
          field: country_key
À toi de jouerAjoute les tests relationships sur fact_loans, écris une description en une phrase pour chaque modèle dans son .yml.
Indice si tu bloquesdbt docs generate affichera automatiquement tes descriptions — c'est ta référence pour comparer, plus tard, avec ce que le LLM propose.
Tu as réussi sidbt test passe entièrement, dbt docs serve montre une description pour chaque modèle.

Week-end 5 — Orchestration avec Airflow

Vendredi — premier Airflow local

ObjectifAirflow qui tourne en local via Docker, interface web accessible.
Concept à connaîtreAirflow orchestre des tâches sous forme de DAGs Python (différents des DAGs dbt — ici des tâches planifiées, pas des modèles SQL). Le docker-compose officiel lance tous les services nécessaires.
À toi de jouerSuis le guide officiel Airflow + Docker Compose (docker-compose up), connecte-toi à l'interface web, lance le DAG d'exemple fourni.
Indice si tu bloquesLe premier démarrage peut prendre plusieurs minutes (initialisation de la base de métadonnées) — patiente avant de tout redémarrer.
Tu as réussi siTu vois l'interface Airflow (localhost:8080) et un DAG d'exemple tourne avec succès.

Samedi — DAG qui exécute dbt

ObjectifUn DAG Airflow avec deux tâches : dbt run puis dbt test.
Exemple guidé (générique) 
from airflow import DAG
from airflow.operators.bash import BashOperator
from datetime import datetime

with DAG("exemple_dag", start_date=datetime(2026, 1, 1), schedule=None) as dag:
    etape_1 = BashOperator(task_id="etape_1", bash_command="echo bonjour")
    etape_2 = BashOperator(task_id="etape_2", bash_command="echo au revoir")
    etape_1 >> etape_2
À toi de jouerÉcris dags/dbt_pipeline_dag.py avec une tâche BashOperator pour dbt run et une pour dbt test, reliées dans le bon ordre.
Indice si tu bloquesLe conteneur Airflow doit avoir accès à ton environnement dbt — monte ton dossier de projet dbt en volume dans docker-compose.yml.
Tu as réussi siLe DAG s'exécute depuis l'interface Airflow et les deux tâches passent au vert.

Dimanche — planification et logs

ObjectifComprendre comment lire les logs d'une tâche en échec et planifier une exécution récurrente.
À toi de jouerCasse volontairement un test dbt, relance le DAG, observe l'échec dans les logs Airflow, corrige, relance. Ajoute un schedule (ex. quotidien) au DAG.
Indice si tu bloquesLes logs d'une tâche sont accessibles en cliquant sur la tâche puis « Logs » — l'erreur dbt complète y est copiée telle quelle.
Tu as réussi siTu peux expliquer, à partir des seuls logs Airflow, pourquoi une tâche a échoué, sans relancer dbt en local.

Week-end 6 — Intégration LLM : génération de tests

Vendredi — profiling des données

ObjectifUn script qui calcule, pour chaque colonne d'un modèle, le taux de nulls, le nombre de valeurs distinctes et les bornes min/max.
Exemple guidé (générique) 
select
    count(*) as n,
    count(*) - count(amount) as nulls,
    count(distinct amount) as distinct_vals,
    min(amount) as min_val,
    max(amount) as max_val
from fact_loans
À toi de jouerÉcris profile_model.py qui prend un nom de modèle et produit ce profiling pour toutes ses colonnes (boucle via information_schema ou DESCRIBE).
Indice si tu bloquesDESCRIBE fact_loans en DuckDB donne la liste des colonnes et leurs types sans les taper à la main.
Tu as réussi siLe script produit un profiling lisible pour au moins 2 modèles.

Samedi — prompt et appel LLM

ObjectifUn prompt qui donne le profiling au LLM et lui demande de proposer des tests dbt au format YAML.
Concept à connaîtreLe prompt engineering consiste ici à donner du contexte structuré (colonnes, types, stats) et à contraindre le format de sortie (YAML valide, tests dbt existants seulement) pour limiter les hallucinations.
À toi de jouerÉcris un prompt listant les colonnes et leur profiling, précisant les tests dbt disponibles (not_null, unique, accepted_values, relationships), demandant une sortie YAML uniquement. Envoie-le à l'API Mistral.
Indice si tu bloquesSi le LLM ajoute du texte autour du YAML, précise dans le prompt : « réponds uniquement avec le bloc YAML, sans aucun texte autour ».
Tu as réussi siTu obtiens une réponse qui ressemble à un vrai fichier schema.yml dbt, même imparfait.

Dimanche — parsing et fichier candidat

ObjectifUn script qui parse la réponse LLM et écrit un fichier schema_llm_candidate.yml séparé (pas encore utilisé par dbt).
Indice si tu bloquesyaml.safe_load(reponse_texte) peut échouer si le LLM a ajouté du texte parasite — extrais d'abord le bloc entre ```yaml et ``` avant de parser.
Tu as réussi siLe fichier généré est un YAML valide (se charge sans erreur avec yaml.safe_load).

Week-end 7 — Intégration LLM : documentation et évaluation

Vendredi — génération de documentation

ObjectifLe LLM propose une description en une phrase pour chaque colonne d'un modèle.
À toi de jouerAdapte le prompt précédent pour demander des description de colonnes plutôt que des tests, à partir des noms de colonnes et d'exemples de valeurs (anonymisés si besoin).
Tu as réussi siTu obtiens une description cohérente et correcte pour au moins 80 % des colonnes d'un modèle.

Samedi — grille de comparaison manuelle

ObjectifUn tableau qui compare, colonne par colonne, tes tests écrits à la main (week-ends 3-4) et les tests proposés par le LLM.
Concept à connaîtrePrécision = (tests LLM corrects) / (total tests proposés par le LLM). Rappel = (tests LLM corrects) / (total tests qu'un humain jugerait nécessaires). Un test « correct » = pertinent métier et passe réellement sur les données.
À toi de jouerPour 3-5 modèles, remplis un tableau (colonne, test humain, test LLM, correspondance oui/non, le test LLM passe-t-il réellement).
Indice si tu bloquesFais tourner les tests LLM candidats avec dbt test --select <modèle> après les avoir copiés temporairement dans un fichier de test, pour savoir s'ils passent vraiment.
Tu as réussi siTu as un tableau rempli et tu peux calculer précision et rappel à la main.

Dimanche — rédaction des conclusions

ObjectifUne page qui résume ce que tu as observé (le LLM est-il meilleur sur not_null que sur des tests métier complexes ? faux positifs récurrents ?).
Tu as réussi siTu peux résumer en 5 phrases, sans notes, ce que ton évaluation a montré.

Grille d'auto-évaluation anti-triche

Avant chaque commit, pose-toi ces questions :

  • Est-ce que je peux fermer ce fichier et le réexpliquer à voix haute, ligne par ligne, sans le relire ?
  • Si je supprime ce bloc de code et dois le réécrire de mémoire demain, est-ce que j'y arriverais à 80 % ?
  • Ai-je passé au moins 20 minutes à chercher par moi-même (documentation, essais-erreurs) avant de demander de l'aide ?
  • Si une IA m'a aidé, est-ce qu'elle m'a expliqué un concept, ou a-t-elle écrit le code final à ma place ?

Si la réponse est « non » à l'une de ces questions, refais la séance avant de continuer. C'est plus lent, mais c'est le but : ce projet sert à apprendre, pas à accumuler un dépôt GitHub de plus.

Après le MVP : extensions possibles

  • Ajouter Great Expectations en complément des tests dbt, et comparer les deux approches.
  • Ajouter MLflow pour tracker systématiquement chaque run d'évaluation (au lieu du tableau manuel).
  • Réintégrer FEWS NET (données géospatiales) une fois à l'aise avec les bases.
  • Passer de 15-20 modèles à un sous-ensemble plus large (50-80) pour un protocole d'évaluation plus robuste statistiquement.
